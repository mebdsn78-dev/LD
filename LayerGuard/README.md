# LayerGuard — مدير الطبقات الأمنية (16 طبقة) لنظام Windows

برنامج Win32 بلغتي C/C++ يشغّل التطبيقات داخل **16 طبقة عزل متدرجة** (0–15)، مع:
- قائمة **الزر الأيمن ← تعديل الطبقة (Change Layer)** + كلمة مرور.
- **جلسة إدخال آمنة**: تجميد عمليات الطرف الثالث + سطح مكتب معزول (`CreateDesktop`).
- **سجل تدقيق** موقّع بسلسلة هاش (SHA-256).
- **حارس USB**: أي كيبورد جديد يُعطَّل فوراً ثم يُسأل المستخدم «هل هذا كيبورد؟».

> ⚠️ لم يُبنَ هذا المشروع ولم يُختبر على Windows في بيئة الإنشاء (لا يوجد مترجم Windows هناك).
> اختُبر فقط منطق السياسات (`layers.c`) على Linux. توقّع بعض أخطاء الترجمة الصغيرة في أول بناء.

## البناء

متطلبات: Windows 10/11، Visual Studio 2022 (Desktop C++)، CMake ≥ 3.20.

```bat
cmake -B build -G "Visual Studio 17 2022" -A x64
cmake --build build --config Release
build\Release\LayerGuard.exe
```

البرنامج يطلب صلاحيات المسؤول (manifest) لأنه يعطّل الأجهزة وينشئ Job Objects.
البيانات تُحفظ في `%ProgramData%\LayerGuard\` (SYSTEM + Administrators فقط).

## أول تشغيل
1. يفتح سطح مكتب آمن لإنشاء كلمة المرور (8 أحرف على الأقل، مرتين).
2. تُعرض لك **عبارة التحقق** (مثل `amber-falcon-river`). تظهر في كل نافذة كلمة مرور؛ **إن ظهرت عبارة مختلفة فلا تُدخل كلمة المرور** (نافذة مزيفة).
3. أضف تطبيقاً بزر «Add App». كل تطبيق جديد يبدأ في **الطبقة 0**.
4. زر أيمن على التطبيق ← **تعديل الطبقة** ← اختر الطبقة ← أدخل كلمة المرور.

## الملفات

| الملف | الدور |
|---|---|
| `layers.c/.h` | جدول الطبقات الـ16 وسياسة الانتقال (خفض حر، رفع بحد أقصى 4 طبقات، الطبقة 15 محجوزة) |
| `sandbox.cpp/.h` | تشغيل التطبيق داخل عزله: AppContainer (0–3)، Restricted Token (4–11)، High منزوع الامتيازات (12–14) + Job Object لكل طبقة |
| `trust.cpp/.h` | تقييم التوقيع الرقمي وتصنيف التطبيق (نظام / موقّع / غير موقّع / غير صالح) |
| `procmon.cpp/.h` | المراقب الفوري للعمليات الجديدة |
| `procfreeze.cpp/.h` | تجميد/استعادة العمليات (`NtSuspendProcess`) مع Watchdog يستعيدها تلقائياً بعد 90 ثانية |
| `securedesk.cpp/.h` | نافذة كلمة المرور على سطح مكتب خاص بـ DACL محدود + عبارة التحقق + مهلة 60 ثانية |
| `layermgr.cpp/.h` | كلمة المرور (PBKDF2-SHA256، 200,000 تكرار)، القفل بعد 5 محاولات، قائمة التطبيقات، منطق الرفع |
| `audit.c/.h` | سجل append-only بسلسلة هاش + أداة فحص السلسلة |
| `usbguard.cpp/.h` | حجر الكيبورد الجديد: تعطيل ← سؤال ← قائمة سماح/منع دائمة |
| `main.cpp` | الواجهة الرسومية (ListView، القائمة اليمنى، عرض السجل) |
| `paths.c/.h` | مجلد البيانات المحمي |

## تدفق رفع الطبقة

```
زر أيمن ← Change Layer ← اختيار الطبقة
  → فحص السياسة (لا قفزة > 4، لا طبقة 15)            [مرفوض ← سجل]
  → قفل بعد 5 محاولات؟                                [مرفوض ← سجل]
  → تجميد عمليات الطرف الثالث (+ Watchdog)
  → سطح المكتب الآمن + عبارة التحقق + إدخال كلمة المرور
  → تحقق PBKDF2 (مقارنة ثابتة الزمن) + مسح الذاكرة
  → نجاح: حفظ الطبقة الجديدة (والتطبيق يُعاد إنشاؤه داخلها)
  → استعادة العمليات المجمّدة (دائماً، حتى عند الخطأ)
  → كل خطوة تُسجّل في Audit Log
```

خفض الطبقة لا يحتاج كلمة مرور (يقلل الصلاحيات). إيقاف حارس USB يحتاجها.

## حارس USB — كيف يعمل وما حدوده

1. عند أول تشغيل: الكيبوردات الموصولة الآن = القاعدة الموثوقة (`usb_allow.txt`).
2. جهاز كيبورد جديد يصل ← **يُعطَّل فوراً** (`SetupDi` + `DIF_PROPERTYCHANGE`) قبل أن يظهر السؤال.
3. المربع الحواري: **«لا» هو الافتراضي**، فلو أرسل الجهاز نفسه «Enter» فلن يوافق على نفسه.
4. «نعم» ← يُضاف إلى `usb_allow.txt` ويُفعَّل. «لا» ← يبقى معطلاً ويُحفظ في `usb_deny.txt`.

**حدود مهمة:**
- الحارس يعمل **بعد** أن يعرّف Windows الجهاز. جهاز مثل Rubber Ducky قد يكتب بضعة ضغطات في أول ثانية قبل التعطيل. للمنع الكامل استخدم أيضاً سياسة **Device Installation Restrictions** (Group Policy) التي تمنع تثبيت أي جهاز جديد قبل الموافقة.
- إن كان كيبوردك الوحيد جهازاً جديداً فاستخدم الماوس للضغط على «نعم».
- جهاز يقلّد **ماوس** أو وحدة تخزين لا يغطيه هذا الإصدار.
- مفتاح الهوية هو Instance ID؛ الأجهزة بلا رقم تسلسلي قد يتغير معرّفها بتغيّر المنفذ.


## التقييم الفوري للتوقيع (trust.cpp)

عند إضافة أي تطبيق، ثم عند **كل تشغيل**، ثم كل 10 ثوانٍ، يُفحص التوقيع الرقمي (Authenticode المضمّن + كتالوجات Windows):

| الحكم | الشرط | الطبقة الابتدائية |
|---|---|---|
| **نظام Windows ✔** | توقيع صالح + الناشر يبدأ بـ Microsoft + المسار الحقيقي داخل `C:\Windows` + مالك الملف TrustedInstaller | **12** (النظيفة) |
| موقّع ✔ | توقيع صالح من ناشر آخر | 0 |
| غير موقّع | لا توقيع | 0 |
| توقيع غير صالح ✘ | توقيع موجود لكنه لا يتحقق (ملف معدَّل) | 0 |

- الحكم يُخزَّن مؤقتاً لكل (مسار، حجم، وقت تعديل)، فأي تعديل للملف يعيد الفحص فوراً.
- إن **ساء** حكم تطبيق بعد الموافقة عليه (مثلاً كان System/Signed وصار Unsigned/Invalid) يُنزَل تلقائياً إلى الطبقة 0 ويُسجَّل في Audit، ولا يُشغَّل حتى تعيد المحاولة.
- أنت من يقرر دائماً: خفض الطبقة حر، ورفعها بكلمة المرور، ويظهر حكم التوقيع داخل نافذة كلمة المرور.
- الطبقة 12 تعمل بـ High Integrity **بعد نزع كل الامتيازات**؛ لذا cmd وping تعمل، أما أوامر تحتاج امتيازات (مثل تحميل Driver، `sfc`، بعض أوامر `netsh`) فستعطي Access denied وهذا مقصود.
- ما يزال ممكناً: DLL sideloading لتطبيق موقّع من ناشر آخر (لذلك لا يُرفع تلقائياً فوق الطبقة 0)، وفترة زمنية صغيرة بين الفحص والتشغيل (TOCTOU).


## المراقب الفوري للعمليات (procmon.cpp)

خيط خلفي يفحص قائمة العمليات كل 400 مللي ثانية. لكل عملية **جديدة** (غير مشغَّلة من LayerGuard) يقرأ مسار الملف ويتحقق من توقيعه ثم يعرضها في الجدول السفلي «Live process».

- العمليات **غير الموقّعة** أو ذات **التوقيع غير الصالح** تُسجَّل في Audit، ويظهر تنبيه (يمكن إيقافه بالمربع «Live alert»): *هل تريد تشغيله داخل الطبقة 0؟* الافتراضي «لا».
- عند الموافقة يُشغَّل أولاً داخل الطبقة 0، **وفقط إن نجح** تُنهى العملية الأصلية (فلا تخسر برنامجك إن فشل الصندوق).
- زر أيمن على أي صف: إعادة التشغيل في الطبقة 0، أو إنهاء العملية (يتحقق أنها نفس العملية وليس PID أُعيد استخدامه).
- عمليات Windows الموقّعة والموقّعة من ناشرين تظهر في الجدول فقط، ولا تُسجَّل في Audit لتجنب الضجيج.

**حدود صريحة:** هذا **كشف بعد البدء** وليس منعاً قبل التنفيذ. العملية بدأت فعلاً حين يصل الحكم، والعمليات الأقصر من 400 مللي ثانية قد لا تُرى، وإعادة التشغيل لا تحفظ وسائط سطر الأوامر. المنع قبل التنفيذ يحتاج Driver (`PsSetCreateProcessNotifyRoutineEx`) أو WDAC/AppLocker.
الطبقة 0 (AppContainer) تحتاج أن يكون الـ exe ومكتباته مقروءة لـ «ALL APPLICATION PACKAGES»؛ برامج مجلد التنزيلات أو المستخدم غالباً لن تعمل فيها (Access denied) ولن تتأثر العملية الأصلية حينها.

## الأيقونة
`src/layerguard.ico` (16–256 بكسل) تُدمج عبر `resources.rc` مع معلومات الإصدار؛ تظهر على الملف التنفيذي والنافذة وشريط المهام.

## الحدود الأمنية الصريحة

- **التجميد ليس ضماناً**: لا يوقف keylogger على مستوى النواة/Driver/Hypervisor/العتاد، ولا عمليات تعمل بصلاحية أعلى. حماية الإدخال الحقيقية تأتي من سطح المكتب المعزول وعبارة التحقق.
- سطح المكتب الخاص **أضعف من UAC Secure Desktop**: أي عملية Administrator/SYSTEM قادرة على فتحه. للعمليات الأشد حساسية فضّل UAC أو Windows Hello.
- Windows فيه 4 مستويات Integrity فقط؛ الفروق بين الطبقات 4–14 تأتي من حدود الـ Job والـ Token، **وليست** 16 مستوى حقيقياً في النواة. الطبقات 12–14 تختلف حالياً بحدود الموارد فقط (تمييز الامتيازات لكل طبقة = تحسين مستقبلي).
- الطبقات 0–3 تحتاج أن يكون ملف الـ exe قابلاً للقراءة من AppContainer (مجلدات Program Files عادةً كذلك؛ مجلد المستخدم لا).
- «إيقاف» التطبيق ينهي العملية الرئيسية فقط؛ الأبناء في الطبقات 0–3 يموتون مع إغلاق LayerGuard (`KILL_ON_JOB_CLOSE`).
- التطبيق يُعاد إنشاؤه عند تغيير الطبقة (لا تُعدَّل عملية حيّة)، فيضيع العمل غير المحفوظ.
- كلمة مرور LayerGuard مستقلة عن كلمة مرور Windows.
- مستثنى من التجميد: الشل، DWM، خدمات النظام، Defender، وكل ما يقع تحت `%WINDIR%`.

## تحسينات مقترحة
- WDAC/AppLocker لفرض الطبقة على مستوى النظام لا على مستوى المشغّل فقط.
- Minifilter/ETW لمراقبة الوصول للملفات لكل طبقة، وتمييز امتيازات الطبقات 12–14.
- خدمة Windows (SYSTEM) تفصل المدير عن الواجهة بدل تشغيل الواجهة كمسؤول.
- توقيع الملفات التنفيذية والتحقق منه قبل السماح بالرفع.
- عاملان للمصادقة (Windows Hello / مفتاح FIDO2) للطبقات ≥ 12.
- Shell Extension حقيقي (`IExplorerCommand`) لقائمة Explorer، وهو يرسل الطلب فقط إلى المدير عبر Named Pipe.
